## Limited-pilot boundary

A pilot cannot safely include document intake/review while all files remain pending scan. A non-document pilot is only a proposal, not a currently verified configuration. Before calling it safe, the Office/project owner must define its feature scope, and engineering/operations must prove in the actual target environment that excluded capabilities are unreachable. At minimum:

- Keep document upload, file access, review, resubmission, archive download and approval out of pilot scope until scanning and clean-file UAT pass. Confirm staff and public routes deny these actions; no existing global pilot flag is assumed.
- Keep WhatsApp dispatch off: verify the actual environment flag is not `true`, no scheduled trigger is active, and any enqueue path cannot dispatch. A missing setting in the checked-in Wrangler file is insufficient proof of remote state.
- Exclude OCR, YKN/Tebliğ Apps Script and extension workflows unless external-service approval and synthetic end-to-end checks are complete. If no existing control can enforce exclusion, add a separately reviewed technical gate before pilot; do not represent a policy-only exclusion as enforced.
- Establish production identity/domain/access, D1/R2, backup/restore, monitoring, incident and rollback controls independently of feature scope.
- Resolve the truthful acknowledgement test path and complete consent owner-session UAT if consent is part of the pilot.

If those off-state and foundational controls cannot be demonstrated without touching production data or sending provider requests, the pilot remains blocked.
